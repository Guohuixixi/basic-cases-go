# 库存扣减题解

题目原文见 `Readme.md` 中的图片。实现保持 `NewInventory`、`Reserve`、`Remaining` 的签名，使用标准库，无数据库、Redis、持久化或记录过期机制。

## 先把题目翻译成例子

初始库存 100：

| 调用 | 返回 | 剩余 |
| --- | --- | --- |
| Reserve("A", 10) | nil | 90 |
| Reserve("A", 10) | nil | 90 |
| Reserve("A", 20) | 数量冲突错误 | 90 |
| Reserve("B", 100) | 库存不足 | 90 |
| Reserve("B", 5) | nil | 85 |

最后一行很关键：失败不记录请求号，因此 B 可以更改数量后再次尝试。成功的 A 则绑定了第一次成功的数量。

## 三个字段各解决什么

- `stock int`：剩余数量，不需要存成 100 个令牌。
- `succeeded map[string]int`：保存成功请求及扣减数量；只存 bool 无法识别数量冲突。
- `mu sync.Mutex`：保护库存与成功记录这一组状态，而不只是保护一次减法。

## Reserve 的顺序

1. 参数校验：空请求号、非正数量直接报错，不改变状态。
2. 上锁，并用 defer 确保所有返回路径都解锁。
3. 查成功记录：同号同数量返回 nil，不同数量返回冲突。
4. 对新请求判断库存是否足够，不足直接报错。
5. 一次性执行 `stock -= qty`，记录 `requestID -> qty`，返回 nil。

必须先查成功记录，再判断库存。假设 A 已扣完全部库存，A 重试时仍应该成功，不能报库存不足。

`Remaining` 也要用同一把锁，否则读取可能与写入发生数据竞争。它返回读取那一刻的快照，不能保证调用返回后库存不再变化。调用方不应先调用 Remaining 判断，再假定 Reserve 一定成功。

## 为什么不会超卖或重复扣减

锁内没有其他请求能够穿插修改。新请求只有在 `stock >= qty` 时才能扣减，因此库存不会为负；同一请求的第二次执行一定能看到第一次成功记录，所以不会再次扣减。同号不同数量并发时，先成功拿到锁并完成扣减的一方确定数量，其他不同数量请求返回冲突；不承诺 goroutine 启动顺序决定胜者。

参数检查在锁外，因为只读当前调用自己的参数。成功记录和库存的所有访问在锁内。构造函数假定 stock 非负，按题意不新增负初始库存的错误接口；实例应通过构造函数创建。Inventory 内含互斥锁，使用后不要复制，方法使用指针接收者。

## 为什么逐个从 channel 取库存容易出错

库存 10，A 和 B 各取 6。如果每次取一个令牌，可能双方各取 5 后一起阻塞：没有任何请求拿够 6，库存却被取空。单次 channel 接收的并发安全，不等于“取 6 个”的整个业务原子性。

即使用非阻塞接收避免挂住，还要回滚已取出的令牌，并处理请求幂等。`len(ch)` 后再循环接收也不是原子检查。这个题用 Mutex 更直接。

channel 并非不能用：可用唯一的管理 goroutine 接收完整的扣减命令，由它独占库存和 map，然后通过响应 channel 返回结果；但这引入管理协程生命周期和通信协议，本题不需要这种复杂度。

## 复杂度与边界

每次 Reserve 的 map 操作平均 O(1)，数量扣减 O(1)，不按 qty 循环。Remaining O(1)。成功记录空间 O(S)，S 为成功的不同请求数；题目不要求清理记录。锁竞争的等待时间不包含在上述本地操作复杂度中。

本实现仅保护同一个进程中同一个 Inventory 实例。多个实例各有独立库存；进程重启不保留记录。这是题目规定的范围。

## 验证

在仓库根目录运行：

```sh
go test -race -count=20 ./algorithm/inventory-decr
go vet ./algorithm/inventory-decr
go run ./algorithm/inventory-decr
```

测试覆盖参数错误、失败后改量重试、同号同量、同号异量、库存耗尽后幂等、500 个不同请求竞争 100 份库存、相同请求并发、不同数量并发竞争，以及两个请求各扣 6 份竞争 10 份库存。并发过程中调用 Remaining，帮助竞态检测发现读写不同步。

`-race` 检查实际执行路径中的数据竞争；没有报告并不等于证明所有业务逻辑正确，所以同时断言库存和各请求返回值。

## 面试时 30 秒解释

我用整数保存库存，用 map 保存成功请求号和数量，再用同一把 Mutex 保护查重、库存判断、扣减和成功记录。相同请求同数量返回成功但不重复扣，数量不同报冲突。库存不足不记录请求，因此允许重试。Remaining 同样加锁，保证并发读写安全。
